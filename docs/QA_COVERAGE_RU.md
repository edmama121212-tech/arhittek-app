## Как выбрать следующую проверку

[Сквозной индекс двух реестров](QA_CROSS_BRANCH_RU.csv) связывает 334 уникальных ID. В 76 строках браузерный исход записан в обеих ветках, в 48 только в PR №95, в 76 только в PR №72. Для 134 строк обе матрицы пока не содержат успешного действия пользователя с проверкой бизнес-результата. Среди них UI-0280, снятый в PR №72, но доступный владельцу в коде PR №95. Таблица в начале документа относится только к матрице PR №95.

Обозначение «UI» указывает ветку, в которой получен результат. По ID в исходном реестре доступны точный бизнес-исход и протокол сборки. Для одного ID ветки могут подтверждать разные последствия. Например, для UI-0006 в PR №95 подтверждено открытие новой карточки, а в PR №72 проверены также отдел и условия строительства. Исправление или подпись из одной ветки могут отсутствовать в другой. [Реестр PR №72](https://github.com/edmama121212-tech/arhittek-app/blob/39b0e76ad6a9e93919535dd42e8950ae9bf38104/docs/QA_CONTROLS_RU.csv) · [Реестр этой сборки PR №95](QA_CONTROLS_RU.csv)

У UI-0164–UI-0179 есть старая разметка доходов и расходов компании. В проверенных маршрутах действующей версии финансов открывается другая форма. Восьми полям и кнопкам отмены из старых форм посвящён отдельный протокол навигации. Распространять результат новой формы на прежнюю нельзя. [Протокол маршрутов](https://github.com/edmama121212-tech/arhittek-app/blob/39b0e76ad6a9e93919535dd42e8950ae9bf38104/docs/QA_LEGACY_FINANCE_ROUTES_RU.md)

С 26 ноября для открытого элемента действует предел в три проверки суммарно, включая повтор после исправления. Первый успешный результат засчитывается сразу. При выборе следующей проверки сверяются оба протокола, пользовательский маршрут и связанный бизнес-результат. Статусы «Обработчик» и «Видимость» требуют проверки действия в интерфейсе. Формирование ссылки для клиента подтверждает адрес и содержимое ссылки, доставка сообщения остаётся отдельным исходом. Состав динамических действий уточняется по ролям и состояниям формы.
