# Покрытие действий в интерфейсе ARHITTEK

В [общем реестре](QA_CONTROLS_RU.csv) собраны 334 уникальные позиции с постоянными ID. Для каждого действия сохранены исходный сценарий, проверенный результат и протокол его сборки. Координаты исходников относятся к моменту инвентаризации.

| Итог | Позиций | Основание |
|---|---:|---|
| Успешное действие через интерфейс | 302 | Подтверждён бизнес-результат в одном или нескольких связанных разделах. |
| Вне рабочего маршрута | 32 | Установлена причина для каждого элемента совместимости, вычисляемого поля или макета. |

В 21 строке каталога появились результаты ручного ввода, сохранения и повторного открытия через пользовательский интерфейс. Число сценариев для каждого поля и фильтра указано отдельно. [Проверки редактора каталога](QA_CATALOG_EDITOR_RUNS.csv)

Шесть пунктов навигации прошли десять вариантов каждый. В протоколе есть целевой экран, количество одновременно активных экранов, признак текущей страницы и время до двух кадров. Четыре фильтра общедоступного каталога проверены на двух ширинах с точной сверкой списка домов после клика. На изолированном серверном контуре карточки четыре поля и кнопка закрытия участвовали в тринадцати вариантах учёта расходов. Суммы в финансах и количество записей проверены до и после перезагрузки браузера. [Навигация](QA_NAVIGATION_RUNS.csv) · [Фильтры каталога](QA_CATALOG_FILTER_RUNS.csv) · [Расходы проекта](../tests/project-expense-finance-ui.cjs)

Столбцы про DOM и клики в матрице отражают измерения из отдельных протоколов. Пустая ячейка означает отсутствие точного сопоставления. Разные размеры экрана одного и того же сценария учитываются как проверки отображения. Результаты на фиктивных данных не подтверждают доставку внешних сообщений, расчёты в рабочей базе или вид интерфейса на физическом устройстве. [Отрисовка](AUDIT_CONTROL_PRESENTATION.csv) · [Нажатия](AUDIT_CONTROL_CLICKS.csv) · [Запуски наборов](QA_SUITE_RESULTS.csv)

Для четырёх динамических действий в финансах присвоены ID UI-0310–UI-0313. Десять элементов этой итерации прошли по 10–12 разных сценариев. Замеры, шаги и наблюдения собраны в [журналах приёмки](QA_DELIVERY_RU.md#продолжение-приёмки-в-pr-68). Общие числа в таблице отражают уровень подтверждения как минимум одного действия. Для остальных элементов объём проверок указан в матрице.

Изменение регулярного платежа (UI-0314) проверено в 12 сценариях, а запись поступления на Главной (UI-0315) — в 10. Подтверждение оплаты в календаре (UI-0316) проверено в 11 сценариях ограничения суммы. ## Происхождение результатов

[Сквозной индекс двух реестров](QA_CROSS_BRANCH_RU.csv) связывает 334 уникальных ID. Для 302 элементов есть успешное действие через интерфейс. У 76 оно подтверждено обеими ветками, у 150 только PR №95, у 76 только PR №72. Ещё 32 элемента не имеют самостоятельного действия в проверенных маршрутах. [Обоснование по каждому ID](QA_INACTIVE_CONTROLS_RU.csv). В таблице в начале документа учтены обе ветки.

Обозначение «UI» указывает ветку, в которой получен результат. По ID в исходном реестре доступны точный бизнес-исход и протокол сборки. Для одного ID ветки могут подтверждать разные последствия. Например, для UI-0006 в PR №95 подтверждено открытие новой карточки, а в PR №72 проверены также отдел и условия строительства. Обе версии включены в общую тестовую сборку. [Реестр PR №72](https://github.com/edmama121212-tech/arhittek-app/blob/39b0e76ad6a9e93919535dd42e8950ae9bf38104/docs/QA_CONTROLS_RU.csv) · [Реестр этой сборки PR №95](QA_CONTROLS_RU.csv)

У UI-0164–UI-0179 есть старая разметка доходов и расходов компании. В проверенных маршрутах действующей версии финансов открывается другая форма. Восьми полям и кнопкам отмены из старых форм посвящён отдельный протокол навигации. Распространять результат новой формы на прежнюю нельзя. [Протокол маршрутов](https://github.com/edmama121212-tech/arhittek-app/blob/39b0e76ad6a9e93919535dd42e8950ae9bf38104/docs/QA_LEGACY_FINANCE_ROUTES_RU.md)

С 26 ноября для открытого элемента действует предел в три проверки суммарно, включая повтор после исправления. Первый успешный результат засчитывается сразу. При выборе следующей проверки сверяются оба протокола, пользовательский маршрут и связанный бизнес-результат. Статусы «Обработчик» и «Видимость» требуют проверки действия в интерфейсе. Формирование ссылки для клиента подтверждает адрес и содержимое ссылки, доставка сообщения остаётся отдельным исходом. Две связи, зависящие от объединения веток, проверены на общей сборке.
