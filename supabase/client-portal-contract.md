# Кабинет заказчика: контракт сервера и условия запуска

Статус: интерфейс `client-portal.html/js/css` готов для изолированной проверки. Рабочий доступ **не активирован**: в HTML `arhittek-client-portal-enabled=false`. Эта настройка — выключатель подключения, а не средство авторизации. В репозитории пока нет подтверждённой реализации серверного адаптера, RLS и приватного хранилища для этого кабинета. Договорной бюджет конкретного объекта и выбранный режим гонорара в рабочую БД не записывались.

## Что есть в приложении

| Механизм | Фактическое использование | Почему не подходит для заказчика |
| --- | --- | --- |
| `verify_employee_pin` | Возвращает employee ID, имя, admin и `session_token`; приложение отправляет `x-session-token` | Это внутренняя роль. `loadAll` читает проекты, ledger, компанию и сотрудников. Роль «Заказчик» в `employees` не делает данные приватными. |
| `logout_session` | Best-effort отзыв employee token при выходе | Серверная реализация и фактические проверки не представлены в репозитории. |
| `catalog.html` | Читает `share_links` по query token, затем `project_cards` | Публичный каталог; сам query token и клиентский фильтр не ограничивают доступ к внутренним таблицам. |
| `tz.html` | RPC `get_tz_form_by_token`, `submit_tz_form`; reference files через public URL | Отдельный редактируемый бриф, не read-only доступ к стройке. |
| Накладные и фотографии | `invoices.photo_url`, `expense_photos.photo_url` из `expense-photos.getPublicUrl` | Публичные URL нельзя превратить в приватные сокрытием ссылки. |
| Этапы | `project_stages` с name, done, due_date, done_at | Нужна серверная привязка к объекту, безопасное публичное название и явная публикация. |

На 19.10.2026 подтверждён P0: запрос с публичным ключом и без пользовательской сессии возвращает ID из внутренней таблицы `company_expenses`. Ранее аналогично проверялись проекты/ledger/сотрудники. Фронтенд-фильтры и закрытый новый endpoint **не устраняют прямой доступ через старые endpoints**. До запуска нужно закрыть этот доступ и проверить всю опубликованную поверхность. Административные ответы RLS/RPC/Storage пока не получены; имена таблиц сессий, текущие тела функций и их права здесь не угадываются.

## Граница доступа

Клиент получает единственное разрешение `construction_client_readonly` на один объект. Он видит публичные названия этапов, проверенные состояния работ, накладные этого объекта, разрешённые файлы, собственные переводы и финансовую сводку объекта. Не выдаются сотрудники, зарплаты, их проценты, резерв и прочие деньги компании, другие заказчики, внутренние заметки, PIN, session token, договора с паспортами или сырые audit changes. Не возвращаются даже скрытые поля «на будущее»: ответ строится явным allowlist, а UI отвергает лишние поля. Отказ UI не отменяет утечку, если сервер уже отправил лишние сведения в сетевой ответ; обязательная защита находится на сервере.

Клиент не входит как сотрудник, не загружает `index.html`, Supabase SDK или публичный ключ базы, не вызывает таблицы. Создание ссылок и их отзыв выполняет только подтверждённый администратор через отдельную серверную авторизацию; она должна быть реализована после чтения реальной схемы сессий. Внешних приглашений текущие файлы не отправляют.

## Ссылки и сервер

1. Сервер создаёт криптографически случайный токен минимум 32 байта. Секрет кодируется base64url (43 символа для 256 бит) либо эквивалентно; UI допускает только 43–128 символов `[A-Za-z0-9_-]`.
2. В серверном приватном хранилище хранится SHA-256/HMAC digest, привязка к **одному** реальному project ID, scope, дата окончания, дата отзыва и автор выдачи. Digest не возвращается клиенту. Raw token выдаётся один раз; токены и Authorization исключаются из логов и аналитики.
3. Ссылка: `https://КОНТРОЛИРУЕМЫЙ-ДОМЕН/client-portal.html#access=СЕКРЕТ`. Query token не принимается. Страница немедленно удаляет fragment и query из адреса через `history.replaceState`; токен остаётся только в памяти вкладки. Он не записывается в localStorage, sessionStorage, IndexedDB, cookies, service worker или кеш.
4. Токен является секретом для просмотра: получивший ссылку получает этот же доступ. Для персональной идентификации клиента вместо такой ссылки нужен отдельный подтверждённый вход клиента с аналогичным серверным scope. Нельзя переиспользовать employee PIN.
5. Выход, pagehide и отзыв/истечение очищают DOM и память; при возвращении видимой вкладки выполняется новая проверка. Отображение обновляется раз в минуту. Уже скачанный получателем файл или уже увиденные сведения невозможно отозвать; отзыв прекращает новые ответы сервера.

UI работает с двумя фиксированными **same-origin** URL относительно каталога страницы:

| Запрос | Тело | Результат |
| --- | --- | --- |
| `POST ./api/client-portal/snapshot` | `{}` | Единственный полный DTO v1 для объекта, найденного **по токену на сервере** |
| `POST ./api/client-portal/document` | `{"document_id":"opaque-id"}` | Поток одного проверенного файла из приватного Storage |

Оба используют `Authorization: Bearer ...`, `credentials: omit`, `cache: no-store`, `redirect: error`, `referrerPolicy: no-referrer`. Сервер отвергает неизвестные ключи тела, project ID, произвольный URL, storage path и bucket. Запросы не изменяют бизнес-данные; POST выбран, чтобы секретные ответы не кешировались привычным GET-маршрутом. Допустим ограниченный журнал просмотра без токенов и без изменения денег.

**GitHub Pages не исполняет API.** Текущий GitHub Pages адрес не обеспечивает серверную активацию. Для запуска нужен HTTPS-домен с тем же origin для страницы и gateway (reverse proxy к проверенному серверу/Edge Function). Если будет выбран отдельный API origin, его надо зафиксировать в исходниках и CSP, настроить точный CORS allowlist и повторить тесты; текущий код произвольные cross-origin API не поддерживает. Запросы и ответы нельзя перенаправлять к API из query/fragment или подменять прямым Supabase select.

Для каждого запроса gateway заново проверяет digest, scope, expiry и revocation. Он определяет project ID сам и получает только разрешённые записи этого объекта. Запрос `document_id` дополнительно проверяет принадлежность документа объекту, его текущую публикацию и разрешённый тип. Подмена ID чужого объекта не должна возвращать ни файл, ни его название, ни размер. Тестирование этой гарантии требует реального серверного адаптера; frontend scope checks сами по себе её не доказывают.

Предпочтителен серверный поток документа вместо публичной ссылки. Bucket должен быть private; Storage не принимает чтение anon, guessed path или токен другого объекта. Существующие public URL подлежащих защите файлов требуется мигрировать, убрать публичные оригиналы и подтвердить, что старые ссылки перестали открываться. Если допускаются короткие signed URLs, они выдаются только после проверки объекта, живут не дольше оставшегося доступа и не могут обеспечить немедленный отзыв уже выданной ссылки; текущий UI ожидает поток, не URL.

Обязательные заголовки: `Cache-Control: private, no-store`, `Pragma: no-cache`, `Vary: Authorization, Origin`, `X-Content-Type-Options: nosniff`, точный разрешённый origin либо отсутствие CORS при same-origin, `Cross-Origin-Resource-Policy: same-origin`. Для страницы добавить HTTP `Content-Security-Policy: frame-ancestors 'none'`, HSTS по принятой конфигурации домена. `frame-ancestors` не работает через meta. JSON: `Content-Type: application/json; charset=utf-8`. Документ: согласованный media type, `Content-Disposition: attachment` с очищенным именем. UI не исполняет HTML/SVG и не открывает iframe.

Gateway возвращает 403/404 без содержательных различий для неверного, истёкшего, отозванного токена или чужого документа; не перечисляет объекты. Нужны rate limit на выдачу/чтение/ошибки, ограничение тела запроса, ограничение размера файла 25 МиБ и JSON 5 МиБ, запрет логирования секретов. Несуществующий/неподключённый API, HTML вместо JSON, неполная выборка, лишнее поле, несовместимая версия или неверная арифметика приводят к закрытому экрану без подстановки нулей.

## DTO v1

Все денежные поля заканчиваются `_kopeks`, являются целыми безопасными числами в копейках RUB. Максимальный модуль одного денежного результата — `1_000_000_000_000` копеек; переполнение или выход за лимит — ошибка, не округлённая финансовая сводка. Даты — `YYYY-MM-DD`, timestamps — UTC ISO с `Z`. `scope_ref` и `project.reference` — одинаковая непрозрачная публичная привязка, не внутренний ID проекта. Смешанная привязка отвергается UI; сервер всё равно обязан проверять реальные project ID независимо от этих полей.

Ниже поля — полный allowlist, неизвестные ключи запрещены на каждом уровне.

`generated_at` не старше пяти минут и не более чем на две минуты в будущем. `access_expires_at` строго позже текущего времени. `complete=true` и `row_counts` гарантируют полную согласованную выборку. Сервер читает всё с пагинацией внутри одного согласованного снимка; частичные страницы не выдаёт как полный отчёт. В UI лимит 10 000 строк на коллекцию/документов и 50 файлов на накладную. Превышение требует отдельной проверенной пагинации по immutable snapshot revision; до её реализации возвращается ошибка, а не усечённые суммы.

Фактические даты поступлений, возвратов, затрат и накладных не позже московского календарного дня `generated_at`. Факты выполнения, проверки и приёмки не позже самого `generated_at`; будущие события не выдаются за уже случившиеся. Плановые сроки этапов и работ могут быть будущими и проверяются отдельно. Подтверждённый непогашенный подотчёт может быть больше подписанного R, если кассовая часть объекта имеет дефицит: UI показывает A отдельно и отрицательный расчётный R−A с предупреждением; искусственное ограничение A≤R не применяется. Если R/A неизвестны, R−A не вычисляется как0.

`stages.status`: planned/in_progress/completed. `work_items.status`: planned/in_progress/completed/accepted. completed и accepted требуют сохранённую `completed_at`; accepted дополнительно `accepted_at`. `inspected_at` — отдельный факт проверки прорабом, не принятие заказчиком. Работы не выводятся как «выполнено» из накладной типа Работа или из оплаты. Количество — строка с точкой, максимум 4 знака после точки; сумма строки округляется один раз до копейки по `quantity × unit_price_kopeks`. Для полной суммы применяется quantity=1. Нельзя отмечать принятие без отдельной сохранённой модели приёмки; этот кабинет только читает.

Все накладные данного объекта входят в публичный денежный реестр с датой, суммой, видом и специально разрешённым названием. Сырой description не публикуется, если он содержит внутреннюю информацию; использовать проверенное public title либо нейтральное «Накладная №…». Все клиентские файлы накладных публикуются через проверенное private хранилище. Пока файл не проверен/не опубликован, `documents=[]`, в интерфейсе это явно показано. Исключение файла не должно скрывать денежную строку или завышать баланс. Договоры с паспортами и внутренние документы в эту коллекцию не входят. `documents` содержат только id/scope/invoice/name/media_type/size; URL/path/bucket запрещены. Допустимы PDF/JPEG/PNG/WebP с соответствующими расширениями, без путей/управляющих символов в имени. Сервер проверяет реальное содержимое файла; UI дополнительно сверяет MIME, базовую бинарную сигнатуру и точный размер. Сигнатура не заменяет серверную обработку файла.

## Деньги и 15%

Внутренний `calcConstrFee`/`projects.fee_percent` сейчас рассчитывает выплаты сотрудникам от расходов. `fee_payment` — выплата сотруднику. Эти поля **не являются** гонораром компании и не подставляются в DTO как его оплата.

Версионные договорные условия строительного расчёта: `budget_basis_amount`, `company_fee_rate:15`, `company_fee_mode:included|on_top`, `company_fee_basis:approved_budget`, `confirmed_at`, `currency:RUB`. Серверный адаптер нормализует их через `ARHITTEKConstructionFinance` (отдельный модуль) и переводит в целые копейки DTO; схема хранения и авторизованная запись договора должны быть реализованы отдельно по фактической базе. UI не читает поля audit log или employee fees как подмену нового договора.

Пусть B — утверждённая договорная база. В обоих режимах гонорар = round(B × 15%, до копейки). Для B=1 млн: included → гонорар150 тыс., работы850 тыс., общая сумма1 млн; on_top → работы1 млн, гонорар150 тыс., общая сумма1,15 млн. Режим должен быть подтверждён владельцем/договором. До этого `terms_confirmed=false`, `fee_mode`, `fee_total_kopeks`, `works_budget_kopeks`, `contract_total_kopeks` равны null; поле `approved_kopeks` может быть null или явно неподтверждённой предложенной базой. UI показывает отсутствие согласованных условий, не выводит фиктивную полную цену. Если ранее уже были подтверждённые записи аллокации F, их факт сохраняется; отсутствие текущего договора не превращает F в0. Корректность нового распределения и допустимый предел требуют серверной проверки договора/ревизии.

Фактические суммы:

| Обозначение | Поле | Источник и правило |
| --- | --- | --- |
| C | received_kopeks | Все действительные поступления клиента компании по этому объекту; равно сумме receipts |
| D | direct_paid_kopeks | Фактически оплачено клиентом напрямую по накладным; равно сумме их direct_paid_kopeks; касса компании не увеличивается |
| P | company_spent_kopeks | Фактические **client-funded** оплаты компанией накладных плюс other_costs; не полная стоимость неоплаченных накладных и не начисленная зарплата. Расходы из уже выделенной доли F не входят в P. |
| F | fee_allocated_kopeks | Подтверждённая отдельная аллокация клиентских денег в гонорар компании, от0 до согласованного гонорара; не новый приход и не employee fee_paid |
| Q | refunded_kopeks | Возвращено заказчику, сумма положительных публичных строк refunds; поля строки такие же, как receipts |
| R | held_kopeks | C − P − F − Q. Отрицательное значение сохраняется и показывает дефицит. Это остаток клиентских средств объекта, включая непогашенный подотчёт, а не вся физическая касса компании. |
| A | accountable_outstanding_kopeks | Подтверждённый **непогашенный** client-funded подотчёт у ответственного; часть R, не дополнительный расход. Требуется модель выдачи/погашения/возврата, а не только сумма всех выдач. |

Суммы оплачено компанией/клиентом по одной накладной вместе не превышают её сумму. `invoice.company_paid_kopeks` в этом клиентском реестре — оплата из средств объекта; собственные расходы компании из гонорара не выставляются клиенту повторно. Накладная и её связанный платёж не списываются дважды. Дополнительные фактические client-funded затраты без накладной обязаны иметь публичную строку `other_costs`, иначе сводка не сходится и UI отказывается показывать её. Вид работ и его сметная сумма сами по себе не списывают деньги. Возвраты заказчику имеют отдельный реестр refunds и уменьшают R один раз; сторно ошибочной операции не представляется как новое реальное движение. Возвраты поставщика/исправления накладных сервер агрегирует в действительные нетто-суммы с сохранением проверяемой истории; нельзя скрывать деньги или подменять их произвольными отрицательными накладными. Если действующая модель не может честно представить такие события, расширить DTO и тесты до активации соответствующего потока.

`classification_ok=false` означает, что источник/назначение части денежных операций, выплаты команды либо погашение подотчёта не подтверждены. Тогда P (`company_spent_kopeks`), R и A строго null, UI показывает необходимость сверки, не0. Известные C, D, F и Q сохраняются и сверяются со своими реестрами. Согласованные в прошлом F нельзя стереть из-за отсутствия текущих terms; при спорной/превышенной аллокации классификация блокируется, записанный факт остаётся видимым. При `classification_ok=true` UI сверяет полную формулу R и P по реестру, а F при подтверждённых terms не превышает согласованный гонорар.

Отдельный расчётный модуль различает `client_resources_with_advances` (R), `client_cash_balance` (R−A) и `client_accountable_advances_issued` (все выдачи). Последнее **не равно** непогашенному подотчёту после чеков и возвратов. До реализации серверного settlement adapter нельзя напрямую выдавать issued за `accountable_outstanding_kopeks`: выставлять classification_ok=false/null, если активные выдачи не удаётся сверить. Физическая касса компании C−все её фактические исходящие−Q отличается от R: расходы из собственной доли гонорара не уменьшают деньги клиента повторно и не публикуются как его затраты.

Gateway использует целые значения `.minor`, не переводит туда-обратно суммы из `.summary`. Соответствие: C←received_by_company, D←direct_client_paid, P←confirmed_client_cash_costs, Q←client_refunds, F←company_fee_allocated, R←client_resources_with_advances. Перед публикацией денежных фактов обязательны успешные `cash_ok`, `invoices_ok` и полное чтение всех источников; отсутствие allocations или null факт не превращается в0. `classification_ok=false` разрешает показать известные факты только при достоверном cash/invoice реестре, оставляя P/R/A=null. Статусы contract_ok/allocation_ok/commitments_complete проверяются по назначению; готовый лимит «можно потратить» этот DTO не обещает. A_outstanding требует отдельной подтверждённой модели settlement и не берётся наугад из выдач.

## Доступ администратора и реальные миграции, необходимые для активации

1. Получить законный административный доступ к Supabase SQL Editor/серверным миграциям и Storage. Это не публичный API key. Не просить и не выводить секреты в чат; использовать штатное подключение сервиса или выполнение SQL владельцем.
2. Прочитать реальную схему, RLS, grants, RPC bodies/SECURITY DEFINER/search_path и Storage policies. Диагностика `supabase/security-audit.sql` предназначена для этого, является read-only. Сначала проверить, как реально валидируется employee session; никаких guessed имён таблиц/правок функций.
3. Исправить глобальный P0: запретить anon/PUBLIC чтение/изменение внутренних таблиц и ограничить authenticated сотрудника его полномочиями. Сохранить публичный каталог/ТЗ только через отдельные проверенные разрешённые RPC/DTO. Не включать глобальный запрет наугад, ломающий вход и существующие потоки: сделать миграцию по диагностике, проверить isolated/staging, затем применить контролируемо.
4. Добавить приватное хранилище grants с digest/expiry/revoked/scope/project, серверное issue/revoke с подтверждённой admin авторизацией, и **read-only** gateway/RPC со строгим разрешённым набором объектов. SECURITY DEFINER при необходимости имеет минимальные права, явный безопасный search_path и внутреннюю проверку токена; execute/revoke grants проверяются отдельно.
5. Добавить реальные договорные условия бюджета, отдельную аллокацию F, публичную модель работ/проверки/приёмки и private document mapping с фактической связью invoice→project. До этого `terms_confirmed=false`, отсутствие незаписанного выполнения не подменяется данными накладных. Изменения денег должны быть атомарными, идемпотентными и авторизованными на сервере.
6. Перенести защищаемые файлы в private Storage и закрыть публичные оригиналы. Сервер не принимает storage path от клиента; lookup только по собственному document ID и токену. Добавить revoke/expiry проверки на каждый поток.
7. Развернуть gateway на контролируемом HTTPS origin, установить заголовки и завершить серверный preflight ниже. Только после его успеха заменить meta на true и выдать владельцу одну проверяемую ссылку. Не отправлять ссылки заказчикам без отдельного поручения.

## Приёмка перед реальным открытием

Локальные UI-тесты: `BROWSER_EXECUTABLE=/tmp/chromium node tests/client-portal.cjs`. Они используют только обезличенные фикстуры и перехваченный локальный API, не рабочую БД. Проверяют gate, malformed/лишние поля/смешанные scope, деньги и режимы15%, ошибки и отзыв, документы, CSP, отсутствие секретов в URL/storage и мобильные ширины. Это **не свидетельство**, что реальные RLS или gateway уже защищены.

Реальный серверный preflight в staging, затем read-only проверка production:

- Без токена, с invalid/expired/revoked и с токеном другого объекта нельзя прочитать внутренние таблицы, snapshot чужого объекта, документ, путь Storage или metadata файла. Проверить REST, RPC, Realtime и Storage, а не только интерфейс.
- Токен A читает только A. Попытка подставить project_id B в snapshot отклоняется; document B по токену A →403/404. Неправильный scope, неподтверждённый сотрудник, anon и обычный authenticated не выдают/не отзывают grants.
- После отзыва новые snapshot и document запросы немедленно отказывают. Страница убирает прежние данные при следующей проверке/возвращении/истечении. Скачанные ранее файлы остаются у получателя.
- JSON не содержит raw project/employee rows, notes, payroll, company reserve, employee IDs, PIN/session, чужих клиентов, фото URL/path/bucket или contract passport. Пограничные количества строк читаются полностью без лимита1000; отказ второй страницы не возвращает partial success.
- C, D, P, F совпадают с отдельной проверкой журнала и первичными документами. Проверить частичную оплату, прямую оплату, неоплаченную накладную, повторную запись/отмену/возврат, employee fee_payment, отрицательный R, обе модели15%, округление и отсутствие повторного списания.
- Накладная Работа без saved work status не становится выполненной/принятой. Принятие и проверка прорабом имеют отдельные записи; клиент не может менять их через read-only API.
- Нет API/document ответов в browser cache/CDN/service worker. Authorization не появляется в логах; старые public URL защищаемых файлов не открываются. Проверить CORS чужого origin, redirects, rate limit, MIME и oversize.
- Issue/revoke и бизнес-операции проверены авторизованным RPC, конкурентным запросом и повтором с idempotency key. Только после этого доступ называют действующим защищённым кабинетом.

## Реализованный серверный адаптер — 20.10.2026

Текущие файлы: `client-portal-gateway.js`, `supabase/functions/construction-client-portal/index.ts` и `supabase/client-portal-draft.sql`. Последний — проверенный установочный SQL для одной миграции, а не доказательство применения в рабочей базе. Его отдельная настройка `settings.enabled=false` не изменяется установкой. Фронтенд `client-portal.html` включается только после опубликованного Edge и проверки общей серверной изоляции. Рабочие счета/накладные и исторические ставки установочный SQL не меняет.

Ставка берётся из сохранённого `projects.fee_percent`: старые 0%, 10%, 20% сохраняются, новые объекты получают 15% в основной форме. В DTO `fee_rate_bps` — эта же явная ставка в базисных пунктах (1000 = 10%). `actual_cost_markup/on_top` описывает наценку поверх документированных расходов, а не процент бюджета и не личную зарплату. Проверка суммы использует целые копейки и округление half-up. Договор v1 остаётся историческим отдельным API и не используется новым кабинетом.

Существующие сохранённые накладные становятся документированной базой после явной публикации администратором текущего состояния. Повторно вводить их в `cost_facts` не требуется: сервер синтезирует факты по стабильным исходным ID под авторством публикации. Платёж накладной не становится вторым расходом. Администратор может отдельно указать, что полнота старого денежного журнала проверена. Без такого подтверждения денежный остаток и распределение затрат — null, а не ноль; сохранённые поступления и документы остаются видимыми. Любое изменение финансовых исходников или сохранённой ставки автоматически сбрасывает действительность подтверждения через fingerprint. Сами исходные деньги не изменяются.

RPC администратора используют существующую проверенную `x-session-token` сессию:

- `get_construction_client_settings(p_project_id uuid)` возвращает `revision`, `published`, `saved_markup_percent`, `cost_facts_complete`, `cash_history_complete`, `portal_enabled`, `public_attachments_pending` и список grants без токенов.
- `configure_construction_client_project(p_project_id uuid, p_published boolean, p_confirm_history boolean, p_confirm_markup boolean, p_expected_revision bigint)` подтверждает именно сохранённую ставку и текущую ревизию. Устаревшая ревизия отклоняется с409. Изменение `projects.fee_percent` этим RPC не выполняется. Отмена публикации отзывает все ссылки объекта.
- `issue_construction_client_grant(p_project_id uuid, p_expires_at timestamptz)` возвращает `{grant_id,access,expires_at}`. Секрет `access` возвращается один раз и помещается только в fragment `#access=...` клиентской ссылки. В таблице хранится SHA-256 digest; максимальный срок30 дней.
- `revoke_construction_client_grant(p_grant_id uuid)` немедленно запрещает следующие запросы снимка и документов.

Edge принимает только `POST snapshot {}` и `POST document {document_id}` на origin `https://edmama121212-tech.github.io`. `Authorization: Bearer <64 hex>` — отдельный256-битный клиентский секрет, поэтому Edge развёртывается с `verify_jwt=false`, выполняя собственную авторизацию через private grant lookup. Сотруднические заголовки не пересылаются; service key остаётся только в окружении Edge. На каждый grant действует серверный лимит60 обращений в минуту. Ресурсы не кэшируются. Ответ снимка строится явным allowlist и ещё раз валидируется до отправки. `project_id` из браузера не принимается ни одним клиентским маршрутом.

Файлы новых накладных хранятся в приватном `construction-documents` с префиксом UUID объекта. Публичный `expense-photos/cards/` каталог сохраняется. Старый объект с публичными оригиналами накладных не публикуется до их контролируемого переноса. Клиентская выдача производит lookup invoice→private Storage, проверяет принадлежность/текущую версию, MIME, размер и сигнатуру файла; после загрузки повторно проверяет grant и версию, затем отдаёт байты. Storage path и signed URL не отправляются клиенту. Изображение повторно не загружается ради публикации, если его исходная накладная уже ссылается на приватный файл.

Для развёртывания Edge в набор source-файлов входят точные текущие версии `supabase/functions/construction-client-portal/index.ts`, `construction-finance.js`, `client-portal.js` и `client-portal-gateway.js`; entrypoint сохраняет этот относительный путь. Нужно передать все зависимости, а не только `index.ts`.

Изолированные проверки: `node tests/client-portal-gateway.cjs` (21 сценарий), `node tests/client-portal-sql.cjs` (27 сценариев). SQL-набор использует отдельный PGlite, минимальную реальную структуру используемых полей и тестовую замену криптографических функций, поскольку в этом рантайме нет pgcrypto. Это проверка авторизации/областей/DDL/связей и сценариев, не сертификация криптографии; в Supabase применяется штатный `extensions.digest(...,'sha256')` и `gen_random_bytes(32)`. Никакие финансовые данные рабочей базы этими тестами не изменяются.

Независимое ревью закрыло два дополнительных случая: чужой private Storage path в своей накладной/явном mapping не проходит проверку первого сегмента UUID; изменение сохранённой ставки не переносит старую дату подтверждения на новую ставку — contract остаётся null до повторной публикации. Публичные подписи накладных берутся из существующего описания материалов/работ, с отдельным явным override и ограничением длины. Внутренние notes не выдаются.

Автоматический document ID определяется стабильно по паре invoice UUID + Storage object UUID. Один снимок многострочной накладной может использоваться несколькими позициями без дублирующегося клиентского document ID; путь и исходный файл при этом сохраняются.
