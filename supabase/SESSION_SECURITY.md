# Session and staff-access deployment

`session-security.sql` is prepared SQL for an atomic Supabase `apply_migration`
operation. It is not a filename generated by the Supabase CLI. It preserves all
employees, PINs, sessions, projects, invoices, ledger entries and balances.

Deploy the employee RPC frontend adapter and the `tz.html` `x-tz-token` adapter
first. The frontend supports both the old safe-column read and the new RPCs.
Then apply the SQL once, run advisors and the postflight query below. The SQL is
idempotent; the isolated test also applies the exact script twice.

## Invariants

- Existing `verify_employee_pin` and `logout_session` signatures and logic stay
  intact. No token or PIN is read into a report. The same random
  `x-session-token` is checked for expiry, employee activity and deletion for
  every request; malformed/absent headers fail closed.
- Browser roles cannot read employee PINs or raw sessions, and cannot TRUNCATE
  application tables. The safe profile RPC returns a colleague's salary as
  null, the caller's salary normally, and all salaries/history to an admin.
- Admin company-money and payroll writes retain their existing paths. A staff
  member sees assigned projects and their own payroll marker. They cannot
  appoint themselves, promote themselves or edit financial conditions.
- The leading designer creates a self-assigned zero-finance card through the
  existing form; `INSERT ... RETURNING` is tested in actual PostgreSQL.
- Existing public product catalogue and active service rates stay public.
  Catalogue editors retain explicit permission. Public construction documents
  are a separate operation; this migration grants staff access only to a
  correctly scoped `construction-documents/{project UUID}/...` private path.
- Old public client briefs keep their exact-token RPC and reference-upload
  flow. The new `x-tz-token` header permits upload into that same form folder
  only; unsigned arbitrary uploads and deletes are removed.
- Staff invoice handlers' writes to derived project caches remain accepted
  for compatibility but cannot change cash/expense values: the old values are
  retained. Current card calculations use original invoice/ledger sources.

## Verification

`tests/session-security.cjs` uses the schema-only, sanitized original metadata
fixture in `tests/fixtures/session-security-baseline.sql` and isolated PGlite
records. No production URL or user data is part of this test.

```sh
node tests/session-security.cjs
```

The test suite covers unsigned/wrong/expired/inactive/deleted sessions;
PIN/salary privacy; row scopes and project membership; leading-designer
creation; unauthorized money/assignment/finish changes; stage toggles and
legacy names; role-aware catalogue writes; object-file reads/writes/upserts;
and token-scoped public brief uploads.

After application, run `session-security-postflight.sql`. It only reads
security/aggregate data, with local browser-role claims rolled back. It never
creates a project, financial entry or real session.

## Rollback and recovery

The complete migration is a single transaction. Any error before its final
`COMMIT` restores the exact previous schema and grants automatically; no
partially installed helper/policy state can commit.

After a successful commit, do **not** restore the former `SELECT true` session
helpers, table-level employee SELECT or anonymous write policies. That would
reopen the verified data leak. The compatible frontend can remain deployed
while the new client portal is disabled and a specific failed policy is fixed.

`session-security-safe-recovery.sql` is the safe recovery operation: it turns
off client publication if the supplementary portal tables exist and notifies
PostgREST to reload its schema. It preserves employee sign-in and the security
barrier; no financial values or employee permissions are rewritten. The
original metadata snapshots are available to the integrator privately for
targeted diagnosis, not as an automatically executed insecure downgrade.

Actual browser login with a user's PIN, camera access and mobile Safari are
not exercised by the PostgreSQL fixture. The unchanged PIN login function
remains the live authentication entrypoint.
