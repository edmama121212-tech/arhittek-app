# Расчет в существующей карточке объекта

Актуальное требование Мансура от19.10.2026: **открытая наценка компании15% сверх подтвержденных общих расходов объекта**. Расходы100 000 + наценка15 000 =115 000. Аванс и изменение планового бюджета наценку не создают. Ниже сначала описана новая версия2; прежняя версия1 оставлена только для явного чтения исторических условий.

Модуль не создает новый ERP/экран и не удаляет существующую карточку. Источники — те же `projects`, `invoices`, `ledger_entries`. Расчет не пишет в базу и не меняет исторические поля `fee_percent`, `fee_paid`, `co_fee_paid`.

## Существующая карточка объекта

В карточке, списке объектов и PDF отдельно показаны денежный журнал и расчет по сохраненным документам. Плановая цена `price` не является базой наценки. В текущей карточке `fee_percent` — ставка открытой наценки компании, независимо от назначения сотрудника. Исторические 10%, 0%, 20%, 0% сохраняются; новые объекты используют 15%.

`getConstructionFinancials(project)` возвращает:

| Поле | Значение |
| --- | --- |
| `received` | Приходы от заказчика на дату расчета |
| `cashOutgoing` / `balance` | Фактические исходящие по журналу / приход минус исходящие |
| `directCosts` / `companyMarkupBase` | Накладные плюс самостоятельные расходы без связи с накладной |
| `companyMarkupRate` / `companyMarkupAmount` | Сохраненная ставка / расчетная наценка на базу в копейках |
| `totalWithMarkup` | База плюс наценка |
| `directPaid` | Документы, отмеченные как оплаченные заказчиком напрямую |
| `calculatedAdvanceBalance` | Приход − (база − прямые оплаты заказчика) − расчетная наценка |
| `companyMarkupRecordedPaid` | Сохраненный старый `fee_paid`, без выдуманного подтверждения платежа или allocation |

Две суммы остатка имеют разное назначение: `balance` — только деньги по журналу; `calculatedAdvanceBalance` — документальный расчет после всех загруженных затрат и наценки, независимо от подтверждения оплаты накладной. Последний не заменяет кассу и не меняет свободный резерв. Все документы и отдельные расходы ограничены текущей датой; удаленные записи исключены. Связанная оплата накладной не создает второй расход. Прямые покупки заказчика входят в базу процента, но не вычитаются повторно из аванса.

`calcConstrFee()` сохраняет совместимую форму результата личных начислений, но возвращает нули `feeAmount`, `mainFeeAmount`, `paid`, `remaining`. Строительная наценка компании не создает личного заработка назначенному исполнителю. Явные начисления за работы `role_payout` и их выплаты остаются отдельными записями. Сами старые условия и финансовые строки не переписываются.

Подпись «по документам» означает сохраненный документированный расход, а не доказанную оплату. Для публикации клиенту строгая модель ниже принимает подтвержденную администратором ревизию тех же источников. Адаптер может сформировать стабильные факты из существующих накладных; повторный ввод покупки не нужен. Изменение источника после подтверждения требует новой ревизии, иначе результат не считается подтвержденным.

## Новая версия2: `actual_cost_markup`

```js
const contract = {
  version: 2,
  project_id: project.id,
  currency: 'RUB',
  company_fee_basis: 'actual_cost_markup',
  company_fee_rate: 15,
  company_fee_mode: 'on_top',
  confirmed_at: '2026-10-19T21:51:00+03:00',
  confirmed_by: 'owner-id',
  revision: 1
};
const result = ARHITTEKConstructionFinance.evaluate({
  projectId: project.id,
  asOf: '2026-10-19',
  contract,
  ledger: completeLedgerRows,
  invoices: completeInvoiceRows,
  allocations: confirmedCompanyFeeAllocations,
  directPayments: confirmedPartialDirectPayments,
  costFactsComplete: true,
  costFacts: confirmedSourceCostFacts,
  costCredits: confirmedSourceCostCredits
});
```

У версии2 **нет обязательной утвержденной цены бюджета как базы процента**. `budget_basis_amount`, `price`, `p.expenses` и назначения сотрудников не меняют наценку. Нужны явные `version:2`, база `actual_cost_markup`, сохраненная ставка, режим `on_top`, дата и автор подтверждения. Новая стандартная ставка —15%; для публикации старых объектов адаптер передает их сохраненные0/10/20%, не переписывает договор. Поддерживается явная ставка от0 до100% с точностью до двух знаков процента, включая явный0; пустая ставка не равна нулевой.

`normalizeContract(v2)` подтверждает только условия; гонорар остается `null` до расчета подтвержденных фактов. `contract_total:null` у версии2 означает, что общая будущая цена объекта не выдумана. Текущая стоимость подтвержденных расходов вместе с наценкой находится в `chargeable_cost_total`.

## Подтвержденные факты затрат

```js
{
  id: 'stable-fact-id',
  project_id: project.id,
  source_type: 'invoice', // или 'ledger' для самостоятельного фактического расхода
  source_id: invoice.id, // UUID исходной строки; не отдельная копия документа
  amount: '100000.00',   // рубли, точно совпадает с исходным документом
  entry_date: '2026-10-19',
  cost_scope: 'project', // или 'company_fee' для явного исключения внутренних затрат
  confirmed_at: '2026-10-19T21:00:00+03:00',
  confirmed_by: 'owner-id'
}
```

Факты должны формироваться подтверждением/классификацией уже существующего документа в карточке, а не повторным ручным вводом той же покупки. Это математический DTO; схема хранения и серверное разрешение операций реализуются отдельно.

- Один документ — один факт с постоянным ID. Другой ID не разрешает начислить процент от того же расхода второй раз.
- Связанная оплата накладной меняет cash и состояние оплаты, но не создает еще один факт затрат. `source_type:'ledger'` для `[invoice-payment:ID]` отклоняется; источником остается накладная.
- Прямая покупка заказчика с `paid_by_client:true` входит в подтвержденные расходы и создает наценку, но не создает приход в кассу компании.
- Самостоятельный фактический `project_expense` может быть источником, если у него нет связи с накладной.
- `role_payout`, `bonus`, приходный аванс, возврат клиенту и подотчет не являются самостоятельными конечными затратами для наценки.
- Выплату команде нельзя наценять без подтвержденного клиентского источника. Оплаченные подрядные работы и внутренние комиссии из доли компании различаются явно.
- Затраты с `funding_source:'company_fee'` не допускаются как наценяемые клиентские расходы. Документы таких затрат можно подтвердить с `cost_scope:'company_fee'`; они сохраняются в исключенной сумме, не в базе нового процента.

`costFactsComplete:true` — явное подтверждение полноты прочитанного и согласованного набора. Пустой подтвержденный набор при отсутствии расходных источников дает базу0 и наценку0, даже если получен большой аванс. Пропущенная накладная/самостоятельный расход, неизвестный scope, неподтвержденный или неверный источник блокируют `costs_ok` и итоговый гонорар.

Отсутствующий `costFacts`, `costCredits` или флаг полноты **не равен нулевым расходам**. Известное подтвержденное подмножество может показываться как `known_confirmed_project_costs`; это не разрешение начислить окончательную наценку.

## Кредиты, возвраты и округление

```js
{
  id: 'stable-credit-id',
  project_id: project.id,
  cost_fact_id: 'stable-fact-id',
  amount: '10000.00',
  entry_date: '2026-10-19',
  confirmed_at: '2026-10-19T21:30:00+03:00',
  confirmed_by: 'owner-id'
}
```

Положительный подтвержденный credit уменьшает конкретный исходный факт. Сумма его кредитов не может превышать исходную стоимость; чужой/неизвестный факт, неподтвержденная запись и уменьшение до даты исходного расхода отклоняются. Кредит внутреннего расхода компании не уменьшает клиентскую базу.

Формулы в целых копейках:

`B = сумма подтвержденных project-фактов − подтвержденные кредиты этих фактов`.

`F = round_half_up(B × rate_basis_points / 10000)`; `chargeable = B + F`. Для новых15% `rate_basis_points =1500`.

Округление выполняется один раз от итоговой net-базы, а не отдельно от каждой частичной оплаты. Пример: расходы100 000, кредит10 000 → база90 000, наценка13 500, текущая стоимость103 500.

**Credit не является фактическим возвратом денег.** Он уменьшает стоимость документа/долг поставщику. Если счет уже оплачен, появляется требование возврата/зачета; `physical_cash_balance` не увеличивается автоматически. Прямые оплаченные деньги клиента D также не уменьшаются без фактического возврата. Возврат неиспользованного аванса заказчику Q уменьшает cash/клиентский фонд, но сам по себе не уменьшает себестоимость и наценку. Эти события нельзя объединять одним типом.

После уменьшения базы ранее выделенная доля компании может превышать новый F. Это `FEE_OVERALLOCATED`; модуль не стирает и не исправляет уже записанный факт выделения автоматически.

## Выходные поля версии2 для карточки и клиентского DTO

`.minor` — копейки, `.summary` — рубли; имена совпадают. `null` нельзя форматировать как0.

| Поле | Содержание |
| --- | --- |
| `gross_confirmed_project_costs` | Полная сумма корректных подтвержденных project-фактов до кредитов |
| `project_cost_credits` | Подтвержденное уменьшение этих фактов |
| `known_confirmed_project_costs` | Известная net-сумма подтвержденного подмножества; не итог при неполноте |
| `confirmed_project_costs` | Итоговая база B, только если `costs_ok:true`; иначе `null` |
| `confirmed_company_costs` | Исключенные внутренние расходы компании за вычетом их кредитов |
| `company_fee_total` | F = сохраненная ставка × B, только при подтвержденных условиях и полной базе; новая стандартная ставка15% |
| `chargeable_cost_total` | B + F; текущие подтвержденные расходы с открытой наценкой |
| `invoice_credit_total` / `invoice_net_total` | Кредиты накладных / стоимость накладных после кредитов |
| `received_by_company` | C: реальные поступления заказчика в компанию |
| `direct_client_paid` | D: реальные прямые оплаты клиента, вне кассы компании |
| `physical_cash_balance` | Касса компании по денежным операциям объекта; не фактическая банковская сверка |
| `client_refunds` | Q: фактические возвраты заказчику |
| `company_fee_allocated` | Уже подтвержденное внутреннее выделение компании, без нового прихода/расхода |
| `unpaid_invoices` | Неоплаченные обязательства по документам, с учетом кредитов; не уже ушедшие деньги |

Остальные денежные поля и инвариант клиентской/компанийной кассы общие с историческим API ниже. `costs_ok` / `cost_facts_complete` должны быть true до показа итоговой наценки. `contract_ok` подтверждает условия, а не наличие достоверных фактов затрат. Неполная база не скрывает известные реальные денежные операции.

Нельзя автоматически считать `fee_paid` старого объекта получением новой наценки, а `fee_payment` без назначения — внутренним выделением F. Это требует отдельного подтверждения значения исторической записи. Исторические строительные ставки10/0/20/0 также не заменяются новой ставкой15%.

## Историческая версия1 и общий кассовый API

**Следующий раздел описывает сохраненную версию1 `approved_budget`, а не новое требование Мансура.** Она применяется только при явном `contract.version:1` и не выбирается автоматически для существующего проекта или версии2. Общие cash/классификация/связи накладных используются обеими версиями.

`construction-finance.js` — чистый модуль без сети, DOM, базы, таймеров и изменений исходных объектов. В браузере: `window.ARHITTEKConstructionFinance`; в Node: `require('./construction-finance.js')`.

Он не заменяет задним числом старые гонорары исполнителей от расходов. Новый агентский договор включается только отдельным явно сохраненным объектом условий. Само наличие строительной категории, `fee_percent:15` или назначенного прораба такой договор не создает.

## Вызов

```js
const result = ARHITTEKConstructionFinance.evaluate({
  projectId: project.id,
  asOf: '2026-10-19', // календарная дата по Москве, передает вызывающий код
  contract: project.construction_contract,
  ledger: completeLedgerRows,
  invoices: completeInvoiceRows,
  allocations: confirmedCompanyFeeAllocations,
  directPayments: confirmedPartialDirectPayments // необязательный отдельный реестр
});
```

Для старого экрана без смены условий:

```js
const cash = ARHITTEKConstructionFinance.cashSummary({
  projectId: project.id,
  asOf: financeToday(),
  ledger: state.ledger,
  invoices: state.invoices // необязательно для cashSummary, обязательно для evaluate
});
if (cash.cash_ok) show(cash.summary.physical_cash_balance);
```

Для старого объекта это **денежный остаток по известным операциям**, а не физическая кассовая сверка. `bank_reconciled:false` обозначает это явно. Значения `p.advance`, `p.balance`, старые авансы, начальная касса, амортизация, проценты исполнителей и статус проекта сюда автоматически не прибавляются.

Проверка условий отдельно: `normalizeContract(contract, {projectId, asOf})`. Проверка/преобразование денег: `toMinor('123.45') === 12345`, `fromMinor(12345) === 123.45`.

## Исторические условия договора версии1

```js
{
  version: 1,
  project_id: 'uuid-of-project',
  currency: 'RUB',
  budget_basis_amount: '1000000.00',
  company_fee_rate: 15,
  company_fee_basis: 'approved_budget',
  company_fee_mode: 'included', // или 'on_top'; не выбирать молча
  confirmed_at: '2026-10-19T10:00:00+03:00',
  confirmed_by: 'owner-id',
  revision: 1
}
```

В исторической версии1 поддерживается именно15% утвержденной базы. Условия с иной ставкой/базой/валютой не преобразуются автоматически. Это сохраненное чтение ранее заданного варианта; для актуального расчета расходов выбирается только явно согласованная версия2.

| Режим | Утвержденная база | Гонорар компании | Лимит работ/материалов | Всего по договору |
| --- | ---: | ---: | ---: | ---: |
| `included` | 1 000 000 | 150 000 | 850 000 | 1 000 000 |
| `on_top` | 1 000 000 | 150 000 | 1 000 000 | 1 150 000 |

Без подтвержденного режима, даты/автора подтверждения, версии, объекта, валюты или допустимой суммы возвращаются `contract_ok:false`, `company_fee_total:null`, `contract_total:null`. Уже записанные поступления/оплаты продолжают рассчитываться независимо от условий.

## Денежные источники

Списки могут содержать все объекты: модуль фильтрует `project_id`. Только активные записи с постоянным строковым `id` и календарной датой `<= asOf` участвуют в расчете. Для суммы допускаются конечное неотрицательное число или десятичная строка максимум с двумя знаками. Суммы операций должны быть положительными. Недостоверная сумма/дата/ID не заменяется нулем.

- Приходы из `ledger`: `advance`, `final_payment`, `income`, `materials_budget`, `construction_budget`.
- Реальные исходящие: `expense`, `project_expense`, `payment`, `withdrawal`, `fee_payment`, `salary_payment`, `client_refund`.
- `role_payout`, `bonus` — начисления, без изменения наличных. Для их полного погашения нужен отдельный проверенный реестр обязательств; отсутствие такой связи показывается в `issues`, а `commitments_complete:false` блокирует неподтвержденный свободный остаток.
- Импорт `Ранее внесённые расходы` / `[cash:historical-expense]` не становится новой оплатой. Нужен исходный подтвержденный денежный документ.
- Связь оплаты с накладной: `invoice_id` или существующий `[invoice-payment:ID]` в `description`. Объект платежа и накладной обязан совпадать. Противоречащие поле/маркер блокируют подтверждение оплаты.
- Накладные имеют `invoice_date`, `amount`, `item_type`, `project_id`, `id`. Неизвестный тип сохраняет стоимость в «Прочее» и создает предупреждение; его нельзя отбрасывать и создавать положительный остаток из прямой оплаты клиента.

`funding_source:'client'` — деньги целевого фонда клиента; `'company_fee'` — расходы компании из уже выделенного ей гонорара. Для обычного безличного `expense` / `project_expense` / `payment` без поля используется клиентский источник, как в действующем журнале. Для выплат с `payee_employee_id`, `fee_payment`, `salary_payment` источник обязателен. Без него сохраняется известный денежный расход, но клиентское распределение возвращается `null`, а сумма попадает в `unclassified_outgoing`.

У `withdrawal` нужны источник и назначение:

- `purpose:'project_expense'` — подтвержденный конечный расход клиента.
- `purpose:'company_fee_expense'` и `funding_source:'company_fee'` — расход компании.
- `purpose:'client_refund'` — возврат денег заказчику. Допускается также отдельный входной `type:'client_refund'`; это API адаптера, не выполненная миграция enum базы.
- `purpose:'cash_handover'` — выданный подотчет, не конечная стоимость материалов/работ. Он уменьшает деньги, оставшиеся у компании, и показывается отдельно.

Произвольный вывод без назначения не подтверждает себестоимость. После появления такой строки реальные cash сохраняются, распределение клиент/компания закрывается до уточнения.

## Выделение гонорара

Массив `allocations` содержит **внутреннее распределение**, не дополнительные проводки income/expense:

```js
{
  id: 'allocation-id',
  project_id: 'project-id',
  amount: '150000.00',
  entry_date: '2026-10-19',
  confirmed_at: '2026-10-19T10:00:00+03:00',
  confirmed_by: 'owner-id'
}
```

Подтвержденные записи суммируются один раз по ID. Выделение сверх 150 000 в приведенном примере вызывает `FEE_OVERALLOCATED`, а не увеличение договорного гонорара. При неподтвержденных условиях сохраненный факт allocation не стирается и не превращается в ноль, но неподтвержденное клиентское распределение блокируется. `fee_paid` и `co_fee_paid` старого проекта не являются такими allocations. Прежнее предположение, что строительный `fee_paid` обязательно является личной выплатой сотруднику, отменено; назначение старой суммы устанавливается по документу, а не по наличию employee_id.

## Прямые оплаты клиента

Существующий `invoice.paid_by_client:true` означает полную прямую оплату счета и не меняет cash компании. Частичные прямые оплаты передаются отдельно:

```js
{id:'direct-id', project_id:'project-id', invoice_id:'invoice-id', amount:'12000.00',
 entry_date:'2026-10-19', confirmed_at:'2026-10-19T10:00:00+03:00'}
```

Нельзя одновременно ставить полную отметку и добавлять отдельные платежи за тот же счет. Модуль вернет `DUPLICATE_DIRECT_PAYMENT_SOURCE`, не неподтвержденный удвоенный итог. Счет на 30 000 с прямой оплатой12 000 и оплатой компании18 000 погашается полностью; cash компании уменьшается только на18 000.

## Результат и интеграция

`.minor` содержит целые копейки; `.summary` — те же поля в рублях. Неподтвержденное значение — `null`, его нельзя пропускать через `Number(null)` / `n(null)` / `||0` и показывать как проверенный ноль.

| Поле | Формула / значение |
| --- | --- |
| `received_by_company` | C: все подтвержденные приходные записи объекта |
| `cash_outgoing` | Все реальные исходящие записи, включая возвраты; каждый ID один раз |
| `cash_payments` | Все реальные исходящие без возвратов |
| `client_refunds` | Q: возвраты клиенту |
| `physical_cash_balance` | C − все реальные исходящие; остаток у компании по журналу объекта |
| `client_funded_cash_payments` | Все клиентские cash выплаты, включая выданный подотчет |
| `company_fee_funded_cash_payments` | Реальные выплаты из доли компании |
| `unclassified_outgoing` | Известные выплаты с неподтвержденным источником/назначением |
| `confirmed_client_cash_costs` | P: конечные расходы клиентского фонда, без подотчета и расходов компании |
| `confirmed_company_fee_cash_costs` | Конечные расходы из выделенного гонорара компании |
| `direct_client_paid` | D: подтвержденные оплаты клиента поставщикам напрямую |
| `total_client_funding` | C + D |
| `client_total_confirmed_cash_costs` | P + D; зарплата/комиссия из выделенного F сюда повторно не попадает |
| `invoice_total` | Стоимость всех активных накладных на дату |
| `unpaid_invoices` | По каждому счету max(0, сумма − подтвержденные оплаты компании − прямые оплаты) |
| `invoice_overpaid` | Подтвержденная переплата, без сокрытия реально ушедших денег |
| `company_fee_total` | Утвержденные15% B, независимо от расходов и назначенного сотрудника |
| `company_fee_allocated` | F: сумма подтвержденных allocations |
| `company_fee_remaining` | max(0, договорный гонорар − F) |
| `client_cash_balance` | C − все client-funded cash выплаты − Q − F; деньги клиента еще у компании |
| `company_fee_cash_balance` | F − company_fee-funded cash выплаты |
| `client_accountable_advances_issued` | A: выданный подотчет из клиентского фонда |
| `client_resources_with_advances` | `client_cash_balance` + A; деньги у компании плюс неподтвержденный подотчет |
| `client_after_invoice_commitments` | Клиентские деньги у компании − неоплаченные накладные; только при полном подтвержденном учете обязательств |
| `client_available_after_reserved_fee` | Предыдущая строка − еще не выделенная часть утвержденного гонорара; F не вычитается повторно |

Инвариант: `client_cash_balance + company_fee_cash_balance === physical_cash_balance`. Поле `.conservation.difference_minor` должно быть нулем; при неподтвержденной классификации `.conservation:null`.

Проверять флаги по назначению: `cash_ok` — сумма денежных операций; `classification_ok` — разделение источников; `invoices_ok` — связность платежей/документов; `contract_ok` / `allocation_ok` — договор и выделение гонорара; `commitments_complete` — полнота подтвержденных обязательств. `.ok` у evaluate означает, что все эти части доступны. `.ok` у cashSummary означает только известный денежный итог. Текст/коды причин — `.issues`.

Для scoped DTO клиентского портала:

- C = `minor.received_by_company`.
- D = `minor.direct_client_paid`.
- P = `minor.confirmed_client_cash_costs` (без прямых D, выделенного F, возвратов Q и выдачи подотчета A).
- Q = `minor.client_refunds`.
- F = `minor.company_fee_allocated`.
- A = `minor.client_accountable_advances_issued`.
- Остаток ресурсов объекта R = `minor.client_resources_with_advances` = C − P − F − Q.
- Из R еще у компании = `minor.client_cash_balance` = R − A.

Сервер должен независимо проверять токен/права и выдавать только данные нужного объекта. Этот модуль не реализует RLS, сохранение terms, storage, клиентские токены или миграции.

## Что эта версия не подтверждает

Значения вычисляются из полностью прочитанных списков. Модуль не узнает, что запрос потерял страницу или недоступен: загрузчик обязан передать полный успешный снимок; отсутствующий `ledger` блокирует cash, отсутствующие `invoices`/`allocations` блокируют соответствующую часть evaluate.

Подотчет пока поддержан как **выданный**, без отдельного механизма погашения принятыми чеками/возвратами прораба. Пока A не погашен в будущей явной модели settlement, `UNSETTLED_ACCOUNTABLE_ADVANCE` и `commitments_complete:false` не позволяют обещать свободный клиентский остаток. Нельзя оформлять оплату чека из подотчета как второй реальный cash расход компании: нужна отдельная неденежная запись погашения/адаптер.

Начисления сотрудников отображаются отдельно; связь долгов с оплатами здесь не придумывается. Выполненные/принятые объемы работ также требуют отдельной сметы/актов, а не вывода из накладной.

Исторический `asOf` исключает будущие даты, но не восстанавливает прежние значения редактированных/удаленных строк по журналу аудита. Это не бухгалтерское закрытие прошедшего периода.
