# ARHITTEK — движение денег и проверка приложения

Дата проверки: 11 октября 2026. Исходная версия: 2a1aa27bccb21a1936f24a907c33cb102d1113bf.

## Результат проверки

Исходная браузерная регрессия: 134/137. Два теста формул не задавали исполнителя после изменения правила начисления; третий проверял прежний текст интерфейса. Тесты уточнены с сохранением проверок формул; добавлен сценарий без назначенного исполнителя.

В отдельном наборе из первых 16 финансовых сценариев исходная версия прошла 3; 13 ошибок воспроизведены на синтетических данных. В исправленной версии проходят:

- 138/138 общих браузерных сценариев;
- 40/40 сценариев движения денег и финансовых экранов;
- отдельные проверки сроков обязательств, кассового снимка и начислений.

Рабочая Supabase в тестах не используется. Все обращения перехватываются и заменяются тестовыми данными. Проверка реального остатка требует фактического журнала операций.

## Структура денег

| Показатель | Источник | Когда меняется касса |
| --- | --- | --- |
| Оплата клиента | Запись аванса, остатка или бюджета в журнале проекта | По фактической дате получения |
| Доход компании | Доход компании или приход без проекта | По дате получения |
| Начисление команде | Процент, индивидуальные м², оклад, премия | Само начисление кассу не меняет |
| Выплата команде | salary_payment или fee_payment с получателем | По дате выдачи денег |
| Прямой расход проекта | Фактический расход в журнале | По дате оплаты |
| Накладная | Стоимость закупки и связанная запись оплаты | При подтверждении оплаты компанией |
| Прямая оплата клиента поставщику | Накладная с paid_by_client | Деньги компании не проходят |
| Расходы компании | Офис, связь, прочее | По дате оплаты |
| Вывод денег | Отдельная запись вывода | По дате вывода |
| Корректировка остатка | Отдельная запись сверки | Меняет остаток, исключена из амортизации |
| Амортизация | 5% фактических поступлений после стартовой сверки | Выделяется внутри денег компании |

Фактический баланс = стартовый остаток + учтённые поступления − учтённые оплаты.

Доступно на расходы = фактический баланс − выделенная амортизация.

Для стартового снимка сохранено прежнее правило: 20 000 ₽ на 05.10.2026 22:26:53 МСК. Операции, уже включённые в этот снимок, не начисляются повторно. Это историческая база расчёта, а не сегодняшний остаток.

В обзоре месяца показаны начало, поступления, оплаты и конец из одного диапазона операций. Для октября отдельно обозначено движение после стартовой сверки. В истории остаются ранние записи с пояснением их участия в остатке. Исторический месяц называется «Прошедший»: серверного бухгалтерского закрытия нет.

## Исправленные ошибки

| Проблема | Исправление |
| --- | --- |
| Месячные поступления включали операции вне расчёта остатка | Сводка и остаток используют один набор учтённых движений |
| В прошлом месяце показывался сегодняшний доступный бюджет | Остаток и амортизация считаются на конец выбранного периода |
| Полный резерв и доступный бюджет возвращались одной функцией | Разделены значения; вывод проверяет доступные деньги |
| Перенос старых расходов создавал новый кассовый расход | Перенос помечается и исключается из новых оплат; накладные стройки повторно не переносятся |
| Слово «сверка» отключало амортизацию настоящего прихода | Исключение определяется категорией корректировки или служебным маркером |
| Редактор терял категорию корректировки | Сохранённая категория включается в список |
| Повторное нажатие создавало несколько доходов, расходов или выплат | Защита от повторного отправления до завершения запроса |
| Будущая выплата показывалась как уже выданная зарплата | Учитывается фактическая дата; новая зарплатная выплата в будущем блокируется |
| Финансовые формы использовали разные календарные даты | Даты и сроки используют московское время |
| Ошибка вставки платежа оставляла увеличенный аванс в проекте | Журнал сохраняется первым; зависимое обновление проверяет исходные суммы; при сбое выполняется компенсация |
| Сбой отмены мог изменить кассу без изменения проекта | Отмена защищена от повторов и компенсируется при сбое зависимого обновления |
| Выплата соисполнителю записывалась на основного исполнителя | Получатель выбирается явно; отмена и восстановление меняют соответствующую сумму |
| Комиссия менеджеру активного проекта не закрывала табель | Выплата сопоставляется с менеджером и расчётным месяцем |
| Переплата скрывалась ограничением «не больше начислено» | Показываются действительная сумма и величина переплаты |
| Старый флаг оплаты выдавался за денежную запись | Старые отметки подписаны отдельно и не создают движения денег |
| Накладная и отдельный расход могли удваивать себестоимость | Их можно связать; себестоимость учитывается один раз |
| Начальные или устаревшие данные выглядели как проверенный остаток | Есть состояние загрузки и предупреждения о сбое обновления или недостающих датах |

## Новые действия

- «Команда»: деньги, выданные в выбранном месяце, и отдельно начисления за расчётный месяц с историей сотрудника.
- «Расходы»: накладная получает связанную оплату. Можно создать фактическую оплату или связать существующий расход. Прямую оплату заказчика нельзя списать с компании.
- Накладная со связанными оплатами не удаляется и не переводится в оплату заказчиком до отмены этих оплат.
- «Резерв»: выгрузка финансовых операций для сверки. В неё не включаются PIN, токены и другие реквизиты доступа сотрудников.

## Границы проверки

Денежные операции остаются клиентскими последовательностями запросов. Проверки исходных сумм и компенсации уменьшают риск рассогласования, но не заменяют серверную транзакцию. Для гарантии однократной записи при одновременной работе разных устройств нужны авторизованные RPC и серверные ограничения. Оплата накладных также требует серверной защиты от одновременного подтверждения на разных устройствах.

Проверены интерфейс и расчёты, включая видимые финансовые панели на ширинах 390 и 360 px. Реальные RLS, схема, сетевые сбои после фактического коммита и точность рабочей истории здесь не подтверждались. Ставки прошлых начислений не заморожены серверным снимком; регулярные настройки остаются локальными.

Изменения не мигрируют рабочие финансовые записи и не устанавливают сегодняшний остаток вручную. Фактическая сверка проводится по рабочей выгрузке.
